# Sawbyte: whole-repository review

**Reviewed:** 3 November 2026. **Code baseline:** [`d70a744cd5094e887278b06feb2aefe7c109e8be`](https://github.com/5ivesaw/Sawbyte/tree/d70a744cd5094e887278b06feb2aefe7c109e8be).

**Verdict: Sawbyte has a real, promising foundation, but it is not a finished automation platform or a ready-to-install launcher app.** The previous “all phases complete” description is substantially ahead of the code. This is more than a few missing finishing touches: important parts of general automation, live state, correctness, launcher operation and testing still need implementation or repair.

This review covers the repository, rather than just the examples mentioned in chat. [The review inventory](REVIEW-INVENTORY.md) accounts for all 61 tracked files at the baseline, including every source module, test, workflow, manifest, document and packaging/branding file. The review traced public commands into their implementations, packet handling, scheduling and tests, and inspected existing GitHub Actions results and downloaded evidence. Third-party dependency implementations were not audited line by line. No software was built or run on the user's machine.

Reading every repository file is not a guarantee that every possible bug has been found. Below, **confirmed** means the source or saved CI evidence directly establishes the finding; **missing** means the advertised/required path is absent from this repository; **unverified** means implementation exists but the necessary evidence does not. Proposed regression checks are future GitHub Actions work, not tests claimed to have run in this review.

## What is real and worth keeping

| Working foundation | What the evidence actually establishes |
|---|---|
| Independent Rust player | `sawbyte-play` connects to a real vanilla server and moves without running the Java client. The native dependency list contains no Azalea gameplay engine. This is a standalone implementation, although dependency inspection alone is not a provenance audit of every line. |
| Movement comparison | Native and normal-client replay match very closely in one 160-tick, flat-world walking/turning/jumping/stopping scenario on Linux. That is a meaningful correctness test. |
| Typed input scheduler | Bounded queues, atomic submission, numeric checks, consecutive ticks, cancellation/release and backend-failure handling have focused tests. Preserve these invariants. |
| Wire foundation | Status/ping has an overall deadline and malformed-input tests. Native framing bounds packet/decompression sizes; an encrypted/compressed stream test checks cipher continuity. |
| Shared replay format | Rust and Java consume the same bounded binary input tape. The lab compares position/ground observations and asserts walking, turning, jumping and stopping. |
| Launcher persistence | Instances, settings and configuration snapshots really are written to disk. Cross-process tests verify persistence. Launch uses a real OS child process. |
| Reusable building blocks | Selector predicates, ordered discrete events, policy interfaces, a budgeted path search, chunk palettes and live observations are useful starting points. Their existence does not establish complete integration. |
| GitHub build infrastructure | Linux x64, Windows x64 and macOS ARM64 native builds/tests pass. The optional Fabric reference bridge builds. Workflows use pinned action revisions, limited permissions and checksummed preview artifacts. |
| Branding | The supplied PNG is used by the README and CI icon generation. Windows executables embed an icon; other artifacts include icon resources. |

The measured baseline is [Build and verify run 41581827822](https://github.com/5ivesaw/Sawbyte/actions/runs/41581827822) and [Real player milestone run 41581827919](https://github.com/5ivesaw/Sawbyte/actions/runs/41581827919), both green at the reviewed commit. ## Misunderstandings corrected in the documentation

The intended product is now recorded in [VISION.md](VISION.md), and the other Markdown files have been aligned with it.

| Earlier interpretation | Actual requirement |
|---|---|
| Make a special multi-screen purchasing feature | Make general operations expressive enough to automate unfamiliar, complex workflows. The user's example is not a product subsystem. |
| JSON is the required scripting language | Choose interfaces and formats on efficiency, coverage and usability. External programs need full control; JSON was illustrative. |
| A command name, enum or successful queue submission means the feature works | The operation needs a connected implementation and an observed outcome. |
| Removing rendering proves the optimization goal | Measure real workloads, reliability, CPU, memory, power and scale. Preserve required behaviour. |
| “No simulation” forbids client-side physics or test doubles | Native clients require prediction and synchronized in-memory state. Fabricated production outcomes are the problem; isolated test fixtures are useful. |
| “No hardcoding” forbids version-specific facts | Correct version data is necessary. Fixed user-example labels, task outcomes and fake transitions are inappropriate. |
| A version label makes that release supported | Each version needs real protocol, data, behaviour and tests. |
| The normal client bridge replaces the standalone project | The independent native client is primary. Normal graphical client integration remains an optional, desired backend. |
| A Gymnasium-shaped class is a complete training environment | Step timing, observations, reset, seeding and external compatibility must actually work. |

These corrections repair the project instructions and status reporting. **They do not repair the code defects below.**

## Findings: general automation and truthful outcomes

Priority **High** means a core promise is broken, a result can be misleading, or ordinary use can fail. **Medium** means a substantial limitation or missing robustness. These are engineering priorities, not numerical estimates of completion.

### A01 — Production code invents state transitions and success · High · Confirmed

[`Session::on_event_emitted`](../native/src/main.rs#L186) changes screens and creates a confirmation event using fixed slots, labels and button IDs. The public workflow command enables this mode and creates a fixture when no real screen exists ([lines 1002–1032](../native/src/main.rs#L1002)). This is in the product path, not only a test. Separately, the chat decoder treats any system message containing “bought” or “purchased” as confirmation ([inventory:480](../native/src/inventory.rs#L480)), without identifying the originating action.

**Impact:** callers can receive a successful result for something the server never did. The repair is general event/state observation and result correlation, with fixture code confined to tests. Do not rebuild this as a more elaborate special purchasing feature. Verify varied workflows against independently observed server changes, including failures and ambiguous outcomes.

### A02 — Workflow waits do not wait for the server · High · Confirmed

[`WorkflowHost` in the live session](../native/src/main.rs#L171) ignores timeout arguments and checks current state once. [`WaitElement` and `WaitField`](../crates/sawbyte-core/src/tasks.rs#L560) also do one immediate check. The entire workflow executes synchronously while the session's packet-processing loop is not advancing.

**Impact:** a legitimate delayed screen/event cannot arrive during the “wait.” Repair with a resumable task/event loop, deadlines, cancellation and state freshness. Test delayed, missing, reordered and disconnected responses; blocking the game loop longer is not a solution.

### A03 — General programming is not exposed through the public interface · High · Missing

[`execute_live_script`](../native/src/main.rs#L644) accepts a fixed whitespace-split command catalogue. The richer Rust `WorkflowStep` representation is not available as a general live request interface. There are no external task handles, generic event subscriptions, reusable function API or comprehensive operation discovery. Python/TypeScript builders mostly concatenate those same command strings.

Programs can run their own loops outside Sawbyte, but cannot compose operations the runtime does not expose or reliably await outcomes it never reports. Build a complete typed command/observation/task interface; select optional scripting/declarative layers around it. A custom language is not itself the requirement.

### A04 — Extension hooks are not a usable extension system · High · Confirmed / missing

`LiveModule` is checked before built-ins, which is useful groundwork, but the executable creates an empty module list and provides no loading/registration API to users. `native` is a binary crate, not an exposed reusable runtime library. [`invoke_extension`](../native/src/main.rs#L237) only inserts an `ext_...` variable; it does not run extension behaviour.

Define the supported extension boundary, registration, state access, lifecycle and errors. Validate an independently written extension through the documented public route, rather than editing the executable's source for each new behaviour.

### A05 — Workflow completion/retry semantics are misleading · High · Confirmed

[`execute_workflow`](../crates/sawbyte-core/src/tasks.rs#L536) reports `Completed` after emitting steps. Its host callback cannot report queue rejection; the live host discards that rejection. `RetryPolicy::Bounded` does not implement retries. `Repeat` silently truncates to 256 iterations, while nested repeats have no shared execution budget. Several failure paths discard prior uncertainty, and a screen wait can clear the irreversible-action flag without proving the earlier action's outcome.

Use explicit accepted/running/completed/failed/cancelled/uncertain results and reject unsupported policies or exceeded budgets. Preserve uncertainty until the relevant outcome is known. Test queue-full, nested work, timeouts and cancellation without duplicate effects.

## Findings: real player rules and action coverage

### A06 — Direct interaction commands bypass the promised player constraints · High · Confirmed

[`interact.mine`](../native/src/main.rs#L734) accepts arbitrary coordinates, assumes the upper face and six ticks. Placement assumes the supporting block and hit position; [`interact.attack`](../native/src/main.rs#L795) accepts an arbitrary entity ID. They do not require the player's actual aim, reach or unobstructed target. The send loop performs no central game-rule revalidation. The separate break-speed helper is not used by live mining.

Move reach/target/rule checks below every API and helper. Derive break/use timing from current version, tool, block and player state. Verify ordinary, obstructed, out-of-range, interrupted and state-changing interactions against the reference client and server outcomes. Direct policy must not disable these rules.

### A07 — Several declared player operations are silently dropped · High · Confirmed

[`encode_serverbound_event_with_table`](../native/src/inventory.rs#L509) ends in `_ => None`; [`tick_live`](../native/src/main.rs#L600) simply skips those events. Mouse-click edges, beacons, books, lecterns, tab completion, dialogs, vehicle steering, fall flying, creative-flight toggling, menus, settings and handoff have types without a native execution path. Attack/use button bits also are not translated into their gameplay semantics by `Player::step`; the movement packet casts the button mask to one byte.

Some operations belong to a graphical adapter rather than a network packet. Each still needs an explicit backend implementation or an unsupported-capability error. Derive a complete operation matrix, expose it, and test every advertised operation. An enum is not coverage.

### A08 — Interaction sequencing and payloads need state-aware execution · High · Confirmed

Mining allocates one sequence number but emits both `base_sequence` and `base_sequence + 1`; the next action can reuse the latter ([tasks:284](../crates/sawbyte-core/src/tasks.rs#L284), [inventory:254](../native/src/inventory.rs#L254)). `UseItem` always encodes yaw/pitch as zero ([inventory:588](../native/src/inventory.rs#L588)). Container clicks always encode empty changed-slot/cursor predictions ([inventory:624](../native/src/inventory.rs#L624)). Basic event validity checks do not validate the current target, screen size, click-mode/button combination or transaction state.

A central executor must own sequences, applicable input state, predictions and acknowledgements. Confirm each payload against the supported version and exercise actual server reconciliation; the current encoder test checks only a packet ID and nonempty bytes.

### A09 — Raycasting can treat unknown obstacles as transparent · High · Confirmed

[`raycast_block`](../native/src/raycast.rs#L128) skips collision lookup errors. Entity occlusion uses this result. Movement/pathfinding generally stop or treat unknown cells as blocked, so targeting has a different and less conservative policy. Selection also reuses movement collision boxes, which are not a complete target/interaction-shape model.

Represent unknown/unloaded/unsupported targeting data explicitly, use the correct versioned selection shapes, and reject unverifiable actions. Test missing chunks, unsupported blocks and non-full-block targets as well as the existing full-cube unit test.

## Findings: observations, inventory and screens

### A10 — Inventory decoding loses ordinary item data · High · Confirmed

[`apply_container_set_content`](../native/src/inventory.rs#L366) stops at a stack with component changes, then returns success. It also breaks on truncated input and defaults some decode errors to zero. Remaining slots and carried cursor contents are not decoded. `apply_container_set_slot` reads count/ID but not components; unknown IDs become fabricated `minecraft:item_N` labels.

Names, lore, metadata and cursor state are prerequisites for general automation, not optional decoration. Decode complete packets into a temporary result, preserve required item components/registries, and commit state only after successful parsing. Test mixed stacks, cursor contents, metadata, removal and malformed packets.

### A11 — Received screen revisions are changed locally · High · Confirmed

The decoder assigns the server's `state_id`, then calls [`ScreenState::set_slot`](../crates/sawbyte-core/src/screen.rs#L144), which increments it. A one-slot update becomes server revision plus one; a full update increments it repeatedly. Field edits also increment the same value.

This undermines the advertised revision checks. Keep authoritative server revision separate from local observation/prediction revisions. Verify that decoding any number of slots preserves the exact server revision and that stale clicks are rejected/reconciled.

### A12 — Screen kinds, widgets and text are mostly models, not live coverage · High · Confirmed

[`apply_open_screen`](../native/src/inventory.rs#L260) recognizes a few numeric menu types and guesses a three-row generic container for everything else. It does not populate live widget/field/trade models. [`fill_field`](../crates/sawbyte-core/src/screen.rs#L327) always returns an anvil rename event, regardless of field/screen kind. `click_widget` maps labels to a container button, which is not a universal UI operation. `gui.click_item` requests the first match rather than enforcing uniqueness.

Build version/backend-specific screen adapters with complete observations and appropriate input semantics, including text editing, focus, dialogs and cursor state. Unknown screens must remain explicitly unknown. Verify across different screen families; no single plugin or example can establish completeness.

### A13 — Packet errors are hidden and structured text is discarded · High · Confirmed

The live dispatcher discards inventory/entity/chat/health decoder errors with `let _ = ...` ([main:455](../native/src/main.rs#L455)). [`Reader::tag`](../native/src/wire.rs#L76) consumes NBT arrays/lists but returns `Null`. Consequently `nbt_to_plain_text` cannot recover list-valued rich-text children and does not resolve translation arguments. No state-freshness/error marker informs consumers that data was lost.

Preserve required data, surface decoding failures, and invalidate affected observations until recovered. Add structured text and malformed packet coverage. A partially updated table must not be presented as a trustworthy current snapshot.

### A14 — Entity tracking is incomplete · High · Confirmed

[`apply_add_entity`](../native/src/inventory.rs#L429) assigns every entity a player-sized box, zero velocity and zero angles. Ordinary relative movement/metadata/equipment updates are not dispatched. A motion packet ID exists but is unused; player knockback and effects are not connected through those updates. Teleport-only tracking cannot maintain general moving-entity observations.

Implement version/type/state-dependent entities and update routing, including removals and dimension changes. Verify different entity sizes, moving targets and observed interactions. Do not advertise general combat/following from an AABB helper alone.

### A15 — Observations omit much of the state programs need · High · Missing

The external interface gives status strings, a map, selected screen summaries and a limited training JSON object. It lacks a complete typed inventory/cursor/component view, coherent world/entity snapshots, subscriptions, freshness, cause/result correlation and exhaustive capabilities. Air/XP fields exist without live updates. `received_events` is an ever-growing string list rather than a bounded, identified event stream.

Design observations alongside every operation. Programs need enough current information to decide and verify actions, not only more command names. Include bounded history and explicit unavailable/unknown fields.

## Findings: world, physics and lifecycle

### A16 — The block profile covers a small selection of the game · High · Confirmed

[`player_lab.py`](../tools/player_lab.py#L52) extracts a short named list of blocks, three slab families and selected special cases. The `stairs` list is never populated. Many ordinary terrain/building states remain unsupported, so moving beyond the fixture can fail collision lookup. Optional profile groups silently discard malformed entries.

Create complete, validated version data with provenance and appropriate state distinctions. Unknown data should have explicit behaviour. Validate varied real worlds and dynamic block changes, not only the flat lab.

### A17 — Collision shapes are approximations · High · Confirmed

[`World::collision_boxes`](../native/src/world.rs#L314) uses one fixed stair arrangement and only a fence centre post. The generator combines walls with fences and honey with soul sand; block orientation/connection/shape properties are not retained. Fluids, vines, ladders and scaffolding are reduced to coarse categories.

Use state-dependent collision/selection/fluid models, including neighbouring-state dependencies where applicable. Compare movement and targeting at boundaries, corners and changing shapes. Existing slab tests are useful but cannot certify the other mechanics.

### A18 — “Complete physics” includes missing and disconnected mechanics · High · Confirmed

[`is_swimming_pose`](../native/src/player.rs#L103) returns `false`; being mounted sets velocity to zero and returns. Gliding changes body/eye size but has no gliding motion model. Flight is set only from initial spectator game mode; abilities/toggling and later game-mode changes are not synchronized. Effects/attributes have fields and formulas but no live update route. Hunger updates a separate table while sprinting reads `Player::food_level`, which remains at its default.

Implement the actual state transitions and mechanics, then extend reference comparisons to each declared mode, terrain, effect and input combination. Formula presence and a compilation pass are insufficient.

### A19 — Chunk mutation assumes a fixed global palette width · Medium · Confirmed limitation

[`Palette::set`](../native/src/world.rs#L92) promotes an overflowing indirect palette to 15 bits regardless of registry size. Larger state IDs can contaminate neighbouring packed values during promotion or be masked on later updates. The profile accepts IDs far beyond that width. Section updates also need strict VarLong termination/overflow validation.

Derive width from validated registry data, bound indices and reject malformed values. Add promotion tests above 16 palette entries, IDs at/above the bit-width boundary, and malformed section updates. Current tests only exercise simple promotion and padding.

### A20 — Respawn, dimension changes and reconfiguration are unfinished · High · Confirmed

[`Session::packet`](../native/src/main.rs#L379) exits on death. The respawn handler only clears velocity and restores a health value; it does not parse/reset dimension/chunks/player state. Reconfiguration switches a flag without a complete lifecycle reset/handshake path. Registry dimensions accumulate. Chunk limits are fixed and startup can wait indefinitely without `--ticks` if the session never becomes ready.

Define lifecycle states and clear/invalidate world, entity, inventory, controls and tasks at the correct transitions. Add readiness deadlines, recovery and explicit respawn/reconnect APIs. Verify deaths, portals, server transfers/reconfiguration, disconnects and failed startup.

### A21 — Packet defaults disagree with the generated protocol report · High · Confirmed

[`PacketTable::default`](../native/src/inventory.rs#L48) uses, for example, player-action `40`, container-content `19`, slot `21`, use-item `64` and use-on `63`. The reviewed CI-generated 26.3 report gives `41`, `18`, `20`, `67` and `66` respectively. The fixture's full table overrides these, masking the problem. Some protocol dispatch remains separately hardcoded.

Require a coherent, validated version adapter/table rather than silently falling back to incorrect values. The unit test that asserts `40` currently reinforces the wrong default. Generate/check both directions and fail for incomplete/mismatched profiles.

## Findings: tasks, policies and scheduling

### A22 — Navigation does not steer toward observed arrival · High · Confirmed and observed

[`compile_navigation_inputs`](../crates/sawbyte-core/src/tasks.rs#L140) allocates fixed ticks per waypoint and assumes a turn has happened while the humanised policy may still be turning. There is no feedback, arrival test, stuck detection or replanning. The saved live trace misses the requested destination while CI passes.

Retain budgeted path search as a building block; add a controller that follows observed position/state and reports actual arrival/failure. Verify varied start headings, policies, terrain, interruptions, changed paths and unreachable goals.

### A23 — Path-search coverage and arithmetic need repair · Medium · Confirmed

[`find_path`](../crates/sawbyte-core/src/tasks.rs#L59) explores horizontal neighbours at the same height or one block up/down, not vertical ladder routes or general swimming/flying/vehicle paths. It reasons in whole cells rather than the player's full collision shape. Manhattan distance times ten can overestimate a combined horizontal/up step costing sixteen, so shortest-path guarantees do not follow. Unbounded public integer coordinates can overflow subtraction/neighbour arithmetic.

Use bounded coordinates, an appropriate heuristic and movement-specific transitions/costs. Separate “route candidate” from verified traversability and report unsupported movement modes explicitly.

### A24 — Named task helpers do not implement complete tasks · High · Confirmed

[`ComposableTask::compile_events`](../crates/sawbyte-core/src/tasks.rs#L284) emits short predetermined sequences. Smelting predicts a revision increment after two ticks; trading waits three ticks; eating imposes a fixed minimum duration. Following returns no events. These helpers have no sustained task state or completion observations, and most are not exposed through the live command interface.

Helpers should compose general observable operations with current-state timing and cancellation. Keep them optional and do not use their names as evidence of crafting, trading, eating or following support.

### A25 — Humanisation mainly covers camera movement · Medium · Confirmed

The native runtime selects humanised/smooth/direct camera policies. GUI cursor and typing policies are only exercised in isolated tests; live clicks and field updates do not call them. GUI coordinates assume a nine-column grid. `WorkflowBuilder(policy=...)` stores a setting but never applies it. Smooth camera jitter can exceed its named maximum speed, and mutable policy parameters have no complete validation.

Wire policies through applicable input surfaces, use actual layouts, define bounds precisely and support explicit off/custom behaviour. Test default/direct/custom operation end to end. No evidence establishes indistinguishability from human play or universal server acceptance.

### A26 — Core cancellation and scheduling guarantees are not integrated into live control · High · Confirmed

The core scheduler's FIFO requires ordered future submissions. A long queued action can prevent a new command scheduled for the next tick. Live control has no exposed stop/cancel/ownership/lease API tying both queues and active workflows together. Client disconnection does not release a held Gym input. Discrete queue errors are swallowed in `tick_live`, and late discrete events can be drained together even though continuous scheduling rejects skipped ticks.

Define task/control ownership, preemption, deadlines, ordering and cancellation across the whole session. Test concurrent controllers, disconnects, queue exhaustion and release failures. The good isolated scheduler tests should remain the foundation.

## Findings: control protocol and SDKs

### A27 — Multiline replies break the line-based TCP clients · High · Confirmed

The native listener writes raw replies containing newlines ([main:1420](../native/src/main.rs#L1420)). Rust's transport reads only one line ([mcp:66](../crates/sawbyte-core/src/mcp.rs#L66)); Python does the same ([SDK:115](../sdks/python/sawbyte/__init__.py#L115)). A map or multiple selector results are truncated; a persistent Python connection can then mistake a leftover line for the next command's response. Rust treats EOF as an empty successful reply.

Frame complete messages with request IDs and explicit errors. Verify multiline text, Unicode, consecutive requests, partial reads and connection closure against the actual native listener.

### A28 — The MCP adapters are not conformant yet · High · Confirmed

Both tool lists omit `inputSchema`. Native calls read `params.script`/`command`, not `params.arguments`; both SDKs produce that private shape. Unsupported tools can fall through to a status operation. The servers advertise resource/prompt capabilities that are incomplete (`prompts/get` is absent; native resource methods are absent). Initialization/version negotiation and notification handling are incomplete.

Use a correct shared implementation and independently exercise discovery, argument validation, notifications, unknown operations and errors. These requirements follow the declared [MCP tools specification](https://modelcontextprotocol.io/specification/2025-06-18/server/tools); JSON-RPC `2.0` is not “MCP 2.0.”

### A29 — The core bridge hand-parses JSON incorrectly · High · Confirmed

[`extract_json_string` / `extract_json_id`](../crates/sawbyte-core/src/mcp.rs#L514) search substrings rather than parse objects. Whitespace before a colon, Unicode escapes, nested keys and string IDs containing punctuation are mishandled; invalid input is not properly rejected. Python's default JSON encoder escapes non-ASCII text, making this relevant to ordinary messages and names.

Use a real bounded JSON parser and structured requests. Test standards-valid formatting, Unicode/surrogates, nested/duplicate keys, ID types, malformed input and notifications. Avoid treating zero dependencies as a reason to implement an incomplete parser.

### A30 — Missing arguments can perform unrelated actions · High · Confirmed

[`tools/call` defaults](../crates/sawbyte-core/src/mcp.rs#L423) include creating a backup, changing FOV and navigating to fixed coordinates. An omitted script is not treated as an invalid request. Unknown resource URIs return launcher state instead of a missing-resource error.

Validate required arguments and operation names. Discovery or malformed calls must not select arbitrary mutations. Remove fixture-like defaults from production adapters.

### A31 — Public control is unbounded and lacks access/ownership controls · High · Confirmed

[`run_live`](../native/src/main.rs#L1381) uses an unbounded control channel, unbounded line reads and one unbounded thread per connection. TCP accepts any supplied bind address without authentication. It drains requests before a game tick with no work budget. Queued requests can execute after the caller's five-second reply timeout, leaving an unknown outcome. Initial-script output can also pollute MCP stdout.

Bound messages, connections and work per tick; define local/remote access, ownership, deadlines and cancellation. Keep diagnostics off protocol stdout. Test slow readers, disconnected callers, excess requests and timeout-before-execution. This directly affects reliability and lightweight operation, even on a trusted local setup.

### A32 — SDK builders cannot safely represent arbitrary arguments · Medium · Confirmed

Python and TypeScript interpolate values into newline/whitespace-delimited scripts without escaping or typed encoding. Paths with spaces break argument counts, consecutive spaces in text are lost by the parser, and a newline in a message/value becomes another command. Python's policy parameter is unused; TypeScript exposes `swarm.spawn` although no runtime handler exists. Selector classes are not connected to the complete selector API.

Use structured arguments with documented validation and shared capability coverage. Test literal whitespace/newlines/Unicode and arbitrary filesystem paths. Remove or clearly reject unsupported builder methods.

### A33 — Python process control can hang and does not implement its stated native mode · Medium · Confirmed

[`SawbyteMcpClient`](../sdks/python/sawbyte/__init__.py#L126) always launches `<binary> mcp --stdio`; substituting `sawbyte-play` cannot construct its required `live` arguments. Requests block on stdout without a deadline, do not correlate response IDs, and pipe stderr without consuming it. Close waits five seconds but has no termination fallback. The raw TCP client returns error strings rather than raising structured errors.

Define supported launch/attach modes and bounded process/request lifecycle. Test missing binaries, process exits, malformed replies, busy stderr and close timeouts.

### A34 — SDK distribution is not verified · Medium · Missing / unverified

TypeScript's package points `main` at `index.ts`, with no build/package script, installed compiler or CI check. Python points its package README outside the SDK tree and CI imports directly from source; wheel/sdist creation and clean installation are not tested. A source import does not prove a distributable package works.

Choose supported SDK distribution formats and test packaged consumers in GitHub Actions. The Python README path needs verification in a built source distribution before publication.

## Findings: neural-network and multi-agent support

### A35 — A training step does not return the result of its action · High · Confirmed

[`gym.step`](../native/src/main.rs#L1129) queues next-tick input and replies immediately. [`SawbyteEnv.step`](../sdks/python/sawbyte/__init__.py#L214) immediately requests another observation. Neither waits for a defined tick boundary or action duration. Buttons persist, so the amount of simulated time per Python call varies with scheduling/network timing.

Define real-time versus controlled-server stepping. Return observations associated with completed action intervals, and test ticks, duration, delay and disconnect behaviour. A client cannot fast-forward an ordinary multiplayer server by naming a method `step`.

### A36 — Reset, seeding and Gymnasium compatibility are incomplete · High · Confirmed

[`reset`](../sdks/python/sawbyte/__init__.py#L205) resets only a Python counter and echoes the seed. It does not reset the world/player or random state. The adapter has no action/observation spaces or full environment contract. Its fixed navigation goal/reward is a sample task, not a general training framework, and game death/disconnection is not represented as an episode outcome.

Keep task rewards configurable and implement explicitly supported reset semantics using a controlled environment. Validate the adapter with independent tooling against the [Gymnasium environment contract](https://gymnasium.farama.org/api/env/), including spaces, step, reset and cleanup. Gymnasium remains an optional adapter.

### A37 — Training observations and swarm claims exceed the implementation · High · Confirmed / missing

`gym.observe` computes a voxel buffer but returns only its length and a solid count, not the actual patch. There are no selectable visible-only/privileged observation modes, visibility mask, complete tensors, recorded episodes or vectorized stepping. No live swarm manager, shared-state isolation model, worker supervision or 64-agent benchmark exists. Merely launching multiple independent processes does not supply those features.

Expose useful versioned observation data, define information visibility and episode boundaries, then measure independent/shared multi-agent workloads. Treat previous claims of a complete swarm/training system as unsupported.

## Findings: launcher, accounts and graphical backend

### A38 — Version and backend selection does not control what launches · High · Confirmed

[`spawn_live_process`](../crates/sawbyte-core/src/launcher.rs#L460) ignores instance version/mode and always launches `sawbyte-play live`. The native handshake and profile check require 26.3. The 26.2 profile is metadata only, and claims bridge support despite the Fabric metadata requiring 26.3.

Implement verified version/backend dispatch and truthful capabilities; reject unsupported choices before acquiring accounts or starting processes. Verify that each selection launches the declared runtime/version.

### A39 — The launcher app/install/update system is still missing · High · Missing

There is a CLI and persistent controller, but no graphical launcher, runtime installer, version-resource downloader, update channel, integrity-checked update/rollback flow or combined install package. Users must manually obtain the native binary and a generated block profile. CLI and native downloads are separate; the native artifact does not include its required block-profile data.

Build a complete fresh-install-to-working-session path on Linux and Windows, with actual process/status/error reporting. Do not present compiled binaries or icon files as a finished launcher app.

### A40 — Account locking does not prevent concurrent use reliably · High · Confirmed

[`acquire_account_lock`](../crates/sawbyte-core/src/launcher.rs#L395) checks only its loaded record and writes a file non-exclusively. Two processes can acquire concurrently; relaunching the same instance is explicitly allowed. `add_account` can overwrite a record and clear its lock. Existing serial reload tests do not exercise contention.

Use an atomic ownership mechanism, identify live owners, prevent duplicate sessions and recover stale locks safely. Verify simultaneous launch, duplicate registration, crashes and restart recovery on every supported OS.

### A41 — Spawn is real, but supervision and cleanup are unfinished · High · Confirmed

The bridge drops the returned `Child`; CLI watches it only with `--wait`. No persistent supervisor handles stop/restart, health or exited processes. Locks can remain when an error happens after acquisition but before `spawn`, and failures writing the PID/state after spawn can leave an untracked live child. All new instances default to the same control port. Stored instance policy/settings are not applied to the native launch command.

Make launch a managed lifecycle with rollback on partial failure, actual readiness, unique/validated ports, process ownership and settings dispatch. Verify failed start, early exit, duplicate port, normal shutdown and launcher restart.

### A42 — Persistence needs validation, conflict handling and safe identities · High · Confirmed

The database is an unescaped pipe-delimited file; account fields are not validated for delimiters/newlines or UUID format. Username validation checks only length, yet the username forms a lock-file path. A name such as `../x` can escape the lock directory when a lock is written/removed. `create_instance` can overwrite an existing record and reset settings/counters. Concurrent writers share one temporary filename and stale full snapshots. Deserialization silently ignores malformed rows.

Validate all identities and paths, use structured/versioned storage, reject accidental duplicates, and make updates atomic under concurrent use. Test traversal/delimiters, corrupt files, interrupted writes and concurrent mutations. The bridge's silent fallback to a shared temporary home on load failure also needs explicit error/recovery behaviour.

### A43 — Backups are configuration snapshots, not instance recovery · Medium · Confirmed limitation

[`backup_instance`](../crates/sawbyte-core/src/launcher.rs#L310) stores selected settings/mode/server data, not installed resources, runtime version artifacts, world data or a complete instance. Secret filtering only matches lowercase `token`/`secret` substrings in setting keys; it is not a general token-free guarantee for arbitrary user values.

Name and document the current scope accurately. Define complete backup/update rollback separately, keep credentials outside general settings, and verify restoration and secret exclusion against that contract.

### A44 — Online authentication exists but is not a complete account experience · Medium · Confirmed / unverified

[`auth.rs`](../native/src/auth.rs#L133) has a real Microsoft device-flow/session-join path and requires a registered application ID. It writes a short-lived access token with exclusive creation and Unix `0600` permissions, which are useful protections. Refresh/expiry handling, platform secure storage, launcher login integration and authenticated-server integration evidence are absent. The reviewed lab uses offline mode with secure profiles disabled.

Implement account lifecycle and renewal and verify legitimate authenticated use separately from the offline lab. Do not infer online/server-wide compatibility from the encryption round-trip unit test. Signed chat/session behaviour and required server-resource policies also need explicit support decisions and tests.

### A45 — Menu/settings/handoff commands do not control a normal client · High · Confirmed

[`ClientController::navigate`](../crates/sawbyte-core/src/mcp.rs#L125) changes an enum and records an event. The caller reports navigation without dispatching it to a graphical client. Settings are written to disk, but no running-client connection applies them. Handoff only changes local state. The native runtime has no graphical menus to navigate.

Route normal-client operations to an actual connected backend and provide real headless lifecycle/configuration equivalents. Report unsupported modes instead of success. Verify visible or directly instrumented client effects and takeover/release behaviour.

### A46 — The optional Fabric bridge remains primarily a replay harness · Medium · Confirmed

[`SawbyteBridge.java`](../bridge/src/main/java/dev/fivesaw/sawbyte/SawbyteBridge.java) replays seven movement controls and camera deltas. Its command file supports only pause/resume handoff, hotbar, respawn and disconnect; errors are swallowed. Reading/deleting a shared command file can lose concurrent updates. There is no shared general live observation/control protocol, complete GUI/text integration or launcher wiring.

Preserve its useful reference role and build optional graphical integration explicitly. Test commands, errors, manual input and screen transitions. Do not make this mod a dependency of the standalone native client.

## Findings: performance, verification and distribution

### A47 — Memory bounds are uneven and “zero allocation” is unsupported · Medium · Confirmed

Packet sizes, scheduler queues and chunk counts are bounded, but control requests/threads, entity storage, received events, screen properties and bridge logs are not comprehensively bounded. Collision queries allocate vectors, packet encoding creates buffers and observation formatting allocates strings. A fast/small fixture cannot establish long-session behaviour.

Add workload budgets, retention, backpressure and allocation/tick profiling. Measure endurance and busy-world workloads before claiming core-wide optimization.

### A48 — The transport benchmark does not compare equivalent work · Medium · Confirmed

[`benchmark_transports`](../crates/sawbyte-core/src/mcp.rs#L461) times binary serialization **and decoding** against JSON formatting only. Its binary byte count adds a frame count to a byte count. There is no network IPC, latency distribution or live workload in the benchmark.

Correct the units and compare equivalent encode/decode or end-to-end operations with realistic workloads. This result cannot choose the final transport or support claims of superiority.

### A49 — Broad efficiency and superiority claims are unmeasured · Medium · Unverified

There are no matched Mineflayer/Azalea/reference workloads, CPU/power reports, allocation profiles, long-duration memory tests or multi-client scaling results. RSS sampling observes the native process over a short interval; it excludes the server and does not establish a comparable full-client process-tree measurement.

Publish reproducible workload definitions, capabilities enabled, hardware/OS, warm-up, process scope and error/reliability results alongside resource measurements. Optimize against these, without turning illustrative memory figures into guarantees.

### A50 — Existing tests can pass without the advertised behaviour · High · Confirmed

The final live lab checks only trace length and displacement ([player_lab:265](../tools/player_lab.py#L265)); it misses the wrong destination and fabricated workflow success. SDK/CLI/MCP tests use loopback mocks that echo commands or return fixed observations. The inventory encoder test asserts incorrect default IDs rather than an independent decoder/server result. The “sprint/sneak/edge/slab” test only asserts sprinting and resulting height.

Keep unit/mocked transport tests, but label their scope. Add independent assertions for actual world, inventory, entity, lifecycle and task outcomes. Include failures; a positive reply from the implementation under test is not an oracle.

### A51 — Verification coverage is narrow across platforms and versions · High · Missing

One Linux survival/flat/offline fixture is the live reference gate. Windows/macOS build success does not demonstrate installation, online login, actual gameplay or desktop integration. There are no broader version/backend capability suites, differential physics corpus, protocol conformance suite, recovery/soak/load tests or complete training tests.

Keep one coverage ledger tying each claim to scenario/version/platform/backend. Add tests as connected capabilities become real, rather than checking off entire phases from a representative demo.

### A52 — CI has enforcement and artifact gaps · Medium · Confirmed

Root formatting fails on a diff; native formatting only uploads a patch and builds the modified runner source. `player.yml` has no pull-request trigger, so ordinary PRs do not automatically run native/bridge/gameplay checks. TypeScript and SDK packages are not built. Runtime data/combined installation are absent. Packaged READMEs link to repository documents/assets that are not all included in the artifact.

Enforce native formatting, run appropriate PR checks and verify installed/package consumers. Preserve GitHub-only builds. Keep generated fixes reviewable rather than silently testing source different from the commit.

### A53 — Icons and OS builds are not desktop distribution · Medium · Missing

The Linux desktop entry runs `sawbyte --help` in a terminal; no installer integrates it or its icon. macOS receives an `.icns` file, not a `.app` bundle. There are no Windows installer, Linux install package, release/update manifest or signed/notarized release flow. Icon embedding on Windows is real but does not create a GUI.

Deliver platform packages for the actual launcher UX and smoke-test clean installs, paths with spaces, updates and uninstall. Distinguish preview artifacts from supported releases.

### A54 — Dependency/release provenance and versioning need completion · Medium · Confirmed / unverified

Root crates are version `0.1.0`; help/MCP/native/SDK/bridge use `0.2.0`. The dependency graph is locked for Rust, but no advisory/license/SBOM gate exists. Java dependencies are versioned without a checked-in dependency-verification manifest, and the lab downloads Fabric API without a pinned digest. The project has an MIT license; this review does not certify every dependency or generated-data redistribution right.

Align release versions, produce dependency/provenance information, and add appropriate GitHub checks. No dependency vulnerability scan or legal clearance is claimed by this audit. Existing action pins, server/HeadlessMC checksums and token-file exclusions are useful controls to preserve.

### A55 — Completion claims are also embedded in code/help · Medium · Confirmed

The old Markdown completion checklists and promotional SVG text have been corrected in this documentation pass. However, CLI capabilities, native help, module comments, SDK descriptions and advertised tool descriptions still call incomplete systems complete/live/general. The launcher module even names `launcher.json` while storing `launcher.db`.

Update these user-facing/code claims with the corresponding runtime repair. Generate capability descriptions from supported operations where practical. Until then, the reviewed [coverage ledger](COVERAGE.md) takes precedence over those claims.

## Additional questions that need targeted verification

These are explicitly **not established failures** from this review:

- Exercise late teleports/corrections and reconfiguration against the 26.3 position/tick sequencing rules. The flat initial-spawn fixture cannot certify those paths.
- Independently decode every interaction packet, including current recipe/item/chat representations; most were never verified against a real outcome.
- Check all movement formulas and floating-point behaviour across headings, collisions, effects, fluids and modes against the real client. Approximate-looking code needs measurements, not guesses about exact parity.
- Fuzz framing, compression, NBT, palettes, event parameters and external requests; existing limits are useful but are not a comprehensive hostile-input review.
- Validate expiry/renewal, authenticated servers, platform credential permissions, clean SDK packages, concurrent persistence and crash recovery on actual supported platforms.
- Audit dependency advisories/licenses and data provenance; no “all dependencies safe” claim follows from a green build or this source review.

## What should happen next

The next work should build the shared foundation that makes **unanticipated behaviours** possible. It should not expand the user's example into another special feature.

1. **Make state and outcomes trustworthy.** Remove production fixture fallbacks, reject unsupported operations, fix decoding/revisions/framing, and add tests that independently observe results.
2. **Finish the general engine boundary.** Expose typed actions, snapshots/events, task handles, cancellation, ownership and capabilities. Make waits resume on real state, and enforce player rules below all controllers.
3. **Complete native behaviour by declared coverage.** Build version data, physics/lifecycle/interaction/screen support and reference tests together. Replace fixed-timing helpers with feedback-driven tasks.
4. **Connect the product experience.** Implement real launcher backend/version dispatch, installation, accounts, supervision and UI; connect the optional normal client through the same meaningful API.
5. **Validate integration and advantage.** Package/test SDKs and MCP independently; define real training/multi-agent semantics; measure reliability and resource use on matched workloads. Ship platform packages through GitHub Actions.

These are dependent workstreams, not a five-item limit on a development session. Independent implementation can proceed together. Completion is determined by working coverage and evidence, not how many files, commands or checkboxes were added.

**Current release judgement:** developer prototype; preserve the real native/movement/build foundation. Not ready to claim comprehensive automation, normal-client parity, complete training support, multiple supported game versions, or a finished launcher app. A percentage would imply a measured total scope that the project does not yet have.
